robot-arm-sim · technical documentation · v2.3

Robot Arm Kinematics Simulator

A browser-based simulator for arbitrary serial robot arms. Define any number of revolute and prismatic joints, edit Denavit–Hartenberg parameters live, and get real-time forward kinematics, collision-aware inverse kinematics, a refined workspace-envelope dome, trajectory record/playback, drag-the-target control and shareable configuration links — no build step, no backend.

Live demo ↗ Source code Test suite (60 tests)

Overview

Everything runs client-side as ES modules — three.js renders, plain JavaScript does the math. No build step, no bundler, no backend.

Free-form chains

Add, remove and reorder revolute & prismatic joints. Edit all four DH parameters (θ₀, d, a, α) plus joint limits per joint — the scene, DH table and DOF count update instantly.

Collision-aware IK

Damped least-squares + cyclic coordinate descent with structured restarts and a validity filter — the solver hunts for a branch that is both converged and collision-free.

Workspace-envelope dome

A translucent shell fitted to the true reach boundary: Monte-Carlo seeded, then refined per direction by coordinate descent so every vertex is a genuinely reachable extreme.

Trajectory record/playback

Capture joint-space waypoints and play them back with smoothstep, wrap-aware blending — the EE leaves a fading trail ribbon behind.

Drag-the-target

Grab the IK marker directly in the viewport; the arm follows live through the full collision + branch-solving pipeline while you pull it.

Shareable configs

The whole chain — names, types, DH params, limits, pose — encodes into a ~400-char URL hash. Send the link, get the same arm.

The mathematics

All kinematics follow the standard Denavit–Hartenberg convention; everything else is numerical methods chosen for robustness over elegance.

Forward kinematics

Each joint contributes one homogeneous transform from four parameters — fixed offset θ₀, d, link length a, twist α — and one variable (θ for revolute, d for prismatic):

$$ {}^{i-1}A_i = \operatorname{Rot}_z(\theta_i^*)\, \operatorname{Trans}_z(d_i)\, \operatorname{Trans}_x(a_i)\, \operatorname{Rot}_x(\alpha_i) $$

The end-effector pose chains them: TEE = A₁ · A₂ · … · An, evaluated in forwardKinematics(). Orientation readout is roll–pitch–yaw extracted from the rotation block. Degrees of freedom use the Grübler–Kutzbach count, which reduces to the number of actuated joints for an open serial chain.

Inverse kinematics — damped least squares

Arbitrary DH chains have no general closed-form IK, so the solver is numerical. The position Jacobian $J \in \mathbb{R}^{3 \times n}$ is computed by central finite differences; each iteration steps the joints by the damped pseudo-inverse:

$$ \Delta q = J^{T}\,(J J^{T} + \lambda^{2} I)^{-1}\, e, \qquad e = p_{\text{target}} - p_{\text{EE}} $$

Only the inner 3×3 system is solved directly (Gaussian elimination with partial pivoting), and per-iteration joint velocity is capped for stability. Damping λ = 0.05 keeps the step well-conditioned near singularities.

Cyclic coordinate descent (CCD)

A second, geometric solver walks the chain tip-to-base and rotates each joint about its axis to align the joint→end-effector vector with the joint→target vector. CCD escapes folded / wrong-branch configurations that pure gradient descent cannot, so every restart seed is tried with CCD first and refined with DLS.

Restarts, limits and validity

  • Limits: revolute joints spanning a full rotation wrap through ±π (they can pass the seam); joints with a real sub-2π range and all prismatic joints clamp.
  • Seeds: current pose → base azimuth to the target (and the opposite branch) → base flip → sign flip → deterministic pseudo-random spreads. A 60 ms budget keeps live dragging responsive.
  • Validity: solveIK accepts an optional validate(q) predicate. The UI passes the collision check, so the solver keeps hunting until a branch is both converged and collision-free — only falling back to a colliding solution when every converged branch fails.
  • Motion: accepted solutions ease toward the goal exponentially in joint space along the shortest wrap-aware path, so the arm glides instead of snapping.

Collision geometry

Links are treated as capsules (radius 0.022 m), joints as spheres (0.05 m). Checks per configuration:

Trajectory interpolation

Waypoint playback eases each joint along the shortest wrap-aware path with a smoothstep blend — zero velocity at waypoints, no joint snapping at the ±π seam:

$$ q_i(t) = a_i + \Delta_{\text{wrap}}(a_i, b_i)\cdot s(u), \qquad s(u) = 3u^2 - 2u^3 $$

where $\Delta_{\text{wrap}}$ folds the signed difference into $[-\pi,\pi)$ for joints whose range spans a full rotation. Loop mode appends a closing segment back to the first waypoint.

The workspace-envelope dome

The cyan dome is not a point cloud and not a guess — it is a triangulated shell fitted to the true outer boundary of the reachable workspace, verified to be azimuth-symmetric to ±2 cm for a symmetric arm.

Why the naive version lied

The first implementation scattered raw Monte-Carlo samples — visually noisy, and it systematically undershot the envelope because random sampling rarely lands on the boundary. Binning then mean-filling gaps did the opposite — it fabricated reach in directions that were never sampled. Neither answered the real question:

$$ R(\hat{d}) = \max \{\, t \ge 0 : t\hat{d} \in W \,\} \qquad \text{for each direction } \hat{d} \text{ from the base} $$

The pipeline

40k FK samples (joints + EE pos)→ bin by direction 72×36→ coordinate-descent refine→ azimuth-transplant diffusion ×6→ last-resort gap fill→ tangential smooth→ triangulate + fresnel dome

1 · Directional sampling

sampleWorkspaceConfigs() draws 40,000 random joint configurations, runs FK on each, and keeps the EE position and the joint values behind it. Positions are binned by direction from the base (azimuth × elevation, 72×36 cells); each cell remembers its farthest sample and the configuration that produced it.

2 · Per-direction refinement

For every occupied cell, refineReach() runs coordinate descent in joint space: perturb each joint by a shrinking step (0.5 rad → 0.012 rad), keep moves that grow the EE's distance along the cell's ray, subject to joint limits, the cell's angular cone (center→corner tolerance ≈ 3.5°) and the floor constraint. The result is a real reachable extreme — the dome can only ever claim reach the arm provably has.

3 · Diffusion + azimuth transplant

Refinement from a single random seed lands in local optima, so each cell re-refines from the best config among itself and its 4-neighbors, for up to 6 rounds until the field converges. When joint 1 is a revolute base rotation, seeds borrowed across azimuth are rotated by the azimuth difference first — rotating J1 rigidly rotates the whole distal chain, so a proven solution transplants exactly. Limited-waist arms skip the rotation automatically, preserving genuinely asymmetric workspaces.

4 · Floor-aware fill & honest holes

Cells still empty after diffusion are truly unsolvable directions — they stay holes, except a small mean-fill pass that gives degenerate thin workspaces (a planar arm's flat ring) enough rows to triangulate. Directions whose rays can never rise above the floor are never filled.

5 · Tangential smoothing without lying

Each vertex slides toward its neighbors' centroid along its own radius-sphere, then is renormalized back to the refined radius. Bin-edge stair steps disappear; the claimed reach in every direction is untouched.

6 · Fresnel rendering

The shell renders as one mesh with a fresnel shader — dark translucent body, rim lighting proportional to $(1 - |\hat{n}\cdot\hat{v}|)^2$ — so you see through the dome while the silhouette glows, and the arm stays readable inside it.

What the dome guarantees — and what it doesn't

Verified shape for the PUMA-style preset: ~0.49 m reach at floor level (the EE physically cannot get closer to the base at that height) bulging to 0.79 m overhead — exactly d₁+a₂+d₄+d₆. The pinch where the dome meets the floor is real physics, not a rendering bug.

Interactive features

Drag-the-target v2.0

The green IK marker is a real raycastable object — grab it and pull. Each pointer move raycasts onto a camera-facing drag plane anchored at the grab point, converts the hit through worldToLocal (viewport is y-up, DH space is z-up), and re-solves IK live. The full pipeline stays engaged: restarts, branch flipping, collision validation — you can literally drag the arm into poses it refuses.

Trajectory record & playback v2.0

+ Waypoint captures the current pose; Play eases through them with smoothstep blending and the same wrap-aware shortest path the IK follower uses. Loop mode chains a closing segment back to the start. Any manual input — a slider grab, an IK solve — cancels playback instantly.

EE trail v2.0

A 1500-point fading ribbon tracks the end-effector in world space. Best combined with trajectory playback — you watch the loop the arm actually draws, which is a fast way to spot wrap artifacts or boundary-hugging paths.

Shareable configurations v2.0

Copy share link serializes the whole chain — names, types, all four DH params, limits, and the current pose — into a versioned base64url JSON blob in the #config= hash (~400 chars for a 6R arm). Opening the link rebuilds the exact arm, no backend involved.

Collision limits

With collision limits (floor + self) on, slider moves bisect to the contact wall instead of teleporting into an invalid pose, IK validates every converged branch, and offending links/joints tint red in the viewport.

Architecture

Eight ES modules, one responsibility each. The math core never touches the DOM or three.js — that's what makes it unit-testable in Node.

index.html→main.js (scene + wiring)→ ui.js (panel)↔dh.jsik.jscollision.jsconfig.jsworkspace.jstrajectory.js↔arm.js (three.js)
ModuleResponsibility

ik.jsPosition Jacobian (finite differences), DLS descent, CCD descent, seed/restart strategy, validate() filtering

arm.jsthree.js scene graph: link/joint meshes per DH frame, target marker + axes, collision tinting, EE trail ribbon, workspace dome mesh, geometry disposal on rebuild
ui.jsJoint editor cards, collision-aware sliders (bisect to wall), IK controls + status, trajectory/record UI, toggles, FK/DH readouts, HUD, animation follower
main.jsRenderer, lights, grid, orbit controls, drag-the-target raycasting, config-from-hash bootstrap, panel hookup, window.__app debug handle
The viewport is y-up while DH convention is z-up: the arm group is rotated −90° about x, and every world-space interaction (drag, marker, trail, dome) converts through localToWorld/worldToLocal — getting this space conversion right was one of the real bugs found during development.
GitHub Pages caches module JS for ~10 min. Every deploy bumps ?v= on every import-map URL and the footer tag — that's why the version string appears in index.html.

Using the simulator

  • Build a chain: load a preset or add revolute/prismatic joints; edit name, type, DH params and slider limits on each card.
  • Drive joints: drag sliders, type values, or hit the 0°/±90°/180° snap chips. With collision limits on, motion bisects to the contact point.
  • IK target: drag the green marker in the viewport, or use the X/Y/Z sliders. Arm follows target solves continuously; Solve IK solves on demand. The marker's RGB arrows show the DH frame.
  • See the reach: toggle workspace dome to render the refined reachable envelope (~2 s one-time compute).
  • Record motion: + Waypoint captures poses, Play blends through them (loop mode optional); enable EE trail to draw the tip's path.
  • Share an arm: Copy share link puts a #config= URL on the clipboard — anyone opening it gets your exact chain and pose.
  • Read the math: live DOF + EE pose in the viewport HUD and panel, plus the generated DH table with the variable of each joint marked.
  • Camera & docs: drag to orbit, scroll to zoom, right-drag to pan; Frames toggles DH axis triads; Reset view restores the camera; Docs ↗ opens this page.
